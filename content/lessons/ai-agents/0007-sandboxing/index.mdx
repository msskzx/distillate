<Callout tone="insight">
**Core Insight:** An agent without a sandbox is a root process with a chat interface. Sandboxing is not a single tool—it is a layered defense strategy combining filesystem isolation, network restrictions, resource limits, and syscall filtering to ensure that even a compromised or misbehaving agent cannot escape its execution boundary.
</Callout>

In Lesson 2, Section 5, we introduced the **Autonomy Ladder**—a tiered model for classifying actions by risk (Tier 0: Pure Read through Tier 3: Irreversible). That model answers *what* an agent is allowed to do. This lesson answers the harder question: *how do we technically enforce those boundaries* so that even a prompt-injected, hallucinating, or malicious model cannot cause real-world harm?

Sandboxing is the engineering discipline of building **execution cages**—constrained environments where agent tool calls run with minimized privileges, isolated resources, and no path of escape to the host system.

## 1. Why Sandboxing Is Non-Negotiable

Without sandboxing, an agent's tool calls execute with the full privileges of the user who launched the agent. This creates an extreme attack surface:

- **Prompt Injection:** A malicious web page or document instructs the agent to `rm -rf /` or exfiltrate SSH keys. Without a sandbox, the agent happily complies.
- **Hallucinated Commands:** The model generates a plausible-but-destructive command (e.g., `DROP TABLE users`) that was never intended by the user.
- **Dependency Exploits:** A compromised npm package or PyPI dependency executes arbitrary code during `npm install` or `pip install`.
- **Infinite Resource Consumption:** A buggy agent loop spawns thousands of processes, exhausting CPU, memory, or disk.

<Callout tone="warning" title="The Root Process Anti-Pattern">
Running an agent as a root or administrator process is the single most dangerous configuration in agent deployment. A single prompt injection becomes a full host compromise. The 2023 incident where an AI coding assistant executed `sudo rm -rf` on a user's home directory is not an edge case—it is the default outcome of unsandboxed execution.
</Callout>

## 2. The Sandboxing Stack: Four Layers of Isolation

Production-grade sandboxing is not a single mechanism—it is a **defense-in-depth stack** where each layer provides independent containment. If one layer fails, the others still protect the host.

- **L1** — **Filesystem Isolation:** The agent sees a read-only root filesystem with a writable `tmpfs` workspace mounted at `/workspace`. Source code is bind-mounted read-only. Sensitive paths (`~/.ssh`, `/etc/passwd`, browser profiles) are either hidden or mounted as empty directories.
- **L2** — **Network Restrictions:** Egress is denied by default. The agent can only reach pre-approved endpoints (e.g., a package registry mirror) via an HTTP proxy that enforces DNS allowlisting. Raw sockets, `curl` to arbitrary IPs, and `nc` are blocked at the firewall layer.
- **L3** — **Resource Limits:** Linux `cgroups` cap CPU (e.g., 1 core), memory (e.g., 512 MB), process count (e.g., 64 PIDs), and disk I/O bandwidth. This prevents fork bombs, memory exhaustion, and disk-filling attacks from impacting the host or other tenants.
- **L4** — **Syscall Filtering:** A `seccomp-bpf` profile whitelists only the ~50 syscalls needed for a development agent (read, write, open, close, mmap, etc.). Dangerous syscalls like `mount`, `ptrace`, `kexec_load`, and `reboot` are blocked at the kernel level.

## 3. Container Runtimes: From Docker to Micro-VMs

Not all sandboxing runtimes are created equal. The choice of container runtime determines the strength of the isolation boundary:

| Runtime | Isolation Model | Overhead | Best For |
| --- | --- | --- | --- |
| **Docker / containerd** | Namespace + cgroup isolation. Shared host kernel. | Low (~50ms startup) | Trusted workloads, CI pipelines, development sandboxes. |
| **gVisor (runsc)** | User-space kernel (Sentry) intercepts all syscalls. Guest kernel is a Go reimplementation. | Medium (~150ms startup, 2-5x syscall overhead) | Multi-tenant SaaS, running untrusted code. |
| **Firecracker** | KVM micro-VM. Dedicated guest kernel per sandbox. Minimal device model. | Low for a VM (~125ms startup) | Serverless (AWS Lambda), high-security isolation. |
| **macOS Sandbox (sandbox-exec)** | Seatbelt profile-based sandbox. Path-based file and network restrictions. | Very low | Local macOS agent development. |

<Callout tone="note" title="Architecture Note">
For agent workloads that execute arbitrary code (e.g., running `npm install` or `bun test`), gVisor or Firecracker provide meaningfully stronger isolation than Docker. Docker's shared kernel means a kernel exploit in the sandbox escapes to the host. gVisor's user-space kernel and Firecracker's dedicated guest kernel eliminate this entire class of escape.
</Callout>

## 5. Filesystem Sandboxing: The First Line of Defense

The filesystem is the most common attack vector for agent escapes. A robust filesystem sandbox must address three independent risks:

- **Path Traversal:** The agent writes to `../../etc/cron.d/backdoor` or `/root/.ssh/authorized_keys`.
- **Symlink Attacks:** The agent creates a symlink from `/workspace/config.json` to `/etc/shadow` and reads it through an allowed path.
- **Device Access:** The agent opens `/dev/sda` directly to bypass filesystem permissions.

<Callout tone="note" title="Pattern: The Read-Only Root + Writable Workspace">
The canonical sandbox filesystem layout mounts the entire root filesystem as read-only (`mount -o remount,ro /`), then overlays a `tmpfs` at `/workspace` with a strict size limit (e.g., 1 GB). Source code is bind-mounted read-only from the host. The agent can write freely inside `/workspace` but cannot modify system files, create device nodes, or escape via symlinks because the kernel enforces the read-only mount at the VFS layer.
</Callout>

```bash
# Example: Setting up a sandboxed filesystem namespace
# Create an isolated mount namespace
unshare --mount --pid --fork --mount-proc /bin/bash

# Remount root as read-only
mount -o remount,ro /

# Create a writable tmpfs workspace
mount -t tmpfs -o size=1g tmpfs /workspace

# Bind-mount source code read-only
mount --bind /home/user/project /workspace/project
mount -o remount,ro,bind /workspace/project

# Hide sensitive paths
mount -t tmpfs tmpfs /root
mount -t tmpfs tmpfs /home/user/.ssh
```

## 6. Network Sandboxing: Controlling Egress

Network egress is the exfiltration channel. An unsandboxed agent can `curl` sensitive files to an attacker-controlled server, participate in a DDoS botnet, or scan internal network services.

- **1** — **Default Deny:** The sandbox starts with no network interfaces. The agent cannot make any outbound connection unless explicitly permitted.
- **2** — **Egress Proxy:** All outbound HTTP/HTTPS traffic is forced through a local proxy (e.g., a sidecar container running `mitmproxy` or a custom allowlist proxy). The proxy enforces URL allowlisting and blocks non-HTTP protocols.
- **3** — **DNS Allowlisting:** The sandbox's DNS resolver only resolves pre-approved domains. Requests to any other domain return `NXDOMAIN`, preventing DNS-based exfiltration and tunneling.
- **4** — **Raw Socket Blocking:** The `CAP_NET_RAW` capability is dropped. The agent cannot create raw IP packets, perform ARP spoofing, or use `ping`/`traceroute` for network reconnaissance.

<Callout tone="warning" title="Gap: The DNS Tunneling Blind Spot">
Even with DNS allowlisting, an attacker can encode data in DNS query subdomains (e.g., `base64-secret.attacker.com`). If the allowlisted domain includes a wildcard DNS record, the exfiltration succeeds. Mitigation: use a DNS firewall that inspects query patterns and blocks high-entropy subdomains.
</Callout>

## 7. Sandbox Escapes: Understanding the Adversary

Sandboxing is an arms race. Understanding how sandboxes are escaped is essential for building effective defenses:

| Escape Vector | Mechanism | Mitigation |
| --- | --- | --- |
| **Kernel Exploit** | A vulnerability in the host kernel (e.g., Dirty COW, Dirty Pipe) allows code execution outside the namespace. | Use gVisor or Firecracker (dedicated kernel). Patch host kernels aggressively. |
| **Symlink Race** | Agent creates a symlink during a TOCTOU window between path validation and file access. | Use `O_NOFOLLOW` flags. Validate paths inside the sandbox, not in the harness. |
| **Resource Exhaustion** | Agent spawns a fork bomb or fills the disk, causing denial of service to the host or other sandboxes. | Enforce cgroup PID limits, disk quotas, and CPU time limits. |
| **Container Breakout via Docker Socket** | Agent mounts `/var/run/docker.sock` and uses the Docker API to spawn a privileged container. | Never mount the Docker socket into a sandbox. Use rootless Docker or a remote builder API. |
| **Side-Channel Attacks** | Agent infers host state through timing, cache behavior, or shared resources. | Use Firecracker (no shared resources). Disable hyperthreading for high-security workloads. |

<Callout tone="note" title="Pattern: The Sidecar Proxy">
Rather than embedding sandbox logic in the harness, deploy a sidecar proxy container that all agent network traffic must traverse. The proxy enforces egress policies, rate limits, and audit logging independently of the agent. This separates the security policy from the agent runtime, making it harder for a compromised agent to disable its own network restrictions.
</Callout>

<Callout tone="note" title="Try This: Audit Your Agent's Sandbox">
If you deploy or use an agent that executes code, audit its sandbox configuration:

1. What container runtime does it use? Is it Docker (shared kernel) or gVisor/Firecracker (dedicated kernel)?
2. Can the agent write to paths outside its workspace? Test: ask it to write to `/etc/hosts` or `~/.ssh/authorized_keys`.
3. Can the agent make arbitrary network connections? Test: ask it to `curl` an external URL that is not a package registry.
4. Are resource limits (CPU, memory, PIDs, disk) enforced? Test: ask it to run `:(){ :|:& };:` (fork bomb) in a safe environment.
5. Is the Docker socket mounted? Check if `/var/run/docker.sock` exists inside the sandbox.
</Callout>
